# 다국어(i18n) 설계

작성: 2026-09-14 · 상태: **설계만 완료, 코드 미착수**

대상 로케일 **ko(기본) / en / ja / zh-TW** 4개를 붙이기 위한 설계다.
지금 저장소에는 i18n 인프라가 하나도 없다(`MessageSource`, `LocaleResolver`,
`messages*.properties`, Thymeleaf `#{...}` 모두 검색 결과 0건). 전부 신설이다.

---

## 1. 현재 상태 실측

| 대상 | 수치 |
|---|---|
| 템플릿 | 50개 중 **48개**에 한글, 한글 포함 라인 **2,303줄** (전체 13,466줄) |
| `th:text` 바인딩 | **185개**뿐 |
| Java 문자열 리터럴 내 한글 | 약 **275건** (예외·검증·플래시 메시지) |
| JS | 11개 파일, **200줄** |
| MyBatis 매퍼 XML | 1,007줄 (`MdTestMapper.xml` 316, `BalanceGameMapper.xml` 302) |
| 공통코드 테이블 | **없음** |

`th:text` 가 185개뿐이라는 것이 핵심이다. 한글 2,303줄의 대부분은 마크업에 그대로 박힌
정적 텍스트이므로, 바인딩을 바꾸는 게 아니라 **없던 바인딩을 새로 만드는** 작업이다.
UI 키를 400~600개로 잡으면 × 3개 언어 = 번역 문자열 1,200~1,800개.

## 2. 로케일 선정

| 로케일 | URL 접두사 | `html lang` | hreflang | 비고 |
|---|---|---|---|---|
| 한국어 | **없음** (루트) | `ko` | `ko`, `x-default` | 기본. 원문 |
| 영어 | `/en/` | `en` | `en` | |
| 일본어 | `/ja/` | `ja` | `ja` | |
| 중국어 번체 | `/zh-TW/` | `zh-Hant-TW` | `zh-Hant` | 대만·홍콩·마카오 |

**간체(zh-CN)는 제외한다.** 중국 본토는 구글 검색과 애드센스가 차단돼 있어, 만들어도
검색 유입과 광고 수익이 사실상 발생하지 않는다. 번체권(대만·홍콩)은 구글 접근이 자유롭고
애드센스 RPM 도 높은 편이다. 본토를 노리려면 바이두 등 별도 채널 공략이 전제이므로
그때 다시 판단한다.

hreflang 값을 `zh-TW` 가 아니라 **`zh-Hant`** 로 두는 이유: 지역이 아니라 문자 체계로
매칭돼야 대만·홍콩·마카오·해외 화교를 한 번에 커버한다. URL 접두사는 가독성 때문에
`/zh-TW/` 를 쓰되 hreflang 값과 다르다는 점을 혼동하지 말 것.

## 3. 두 층위를 분리한다

`ddcode` 같은 공통코드 테이블 하나로 묶지 않는다. 성격이 다르다.

| | UI 문구 | 콘텐츠 데이터 |
|---|---|---|
| 예 | "로그인", "삭제하시겠습니까?" | 테스트 제목·문항·결과 본문, 밸런스게임 선택지 |
| 바꾸는 사람 | 개발자 (코드와 함께) | 운영자 (어드민 화면) |
| **저장소** | **`messages*.properties`** | **DB 번역 테이블** |

UI 문구를 DB 에 넣지 않는 이유는, 그 방식의 유일한 장점이 "비개발자가 배포 없이 수정"인데
이 프로젝트는 문구를 고칠 사람이 한 명이고 이미 WAR 배포 경로가 있어서 그 이득이 0이기
때문이다. 대신 치를 비용(페이지당 수십 쿼리, 키 오타가 런타임에야 발각, git 히스토리 상실,
로컬 개발에 DB 덤프 필요)만 남는다.

## 4. URL 전략

### 경로 접두사를 쓴다

```
https://moondap.com/test/abc        ← 한국어 (기존 URL 그대로)
https://moondap.com/en/test/abc
https://moondap.com/ja/test/abc
https://moondap.com/zh-TW/test/abc
```

**한국어를 `/ko/` 로 옮기지 않는다.** 이미 색인된 URL 이 전부 바뀌면 사이트 전체에
301 을 걸어야 하고 축적된 색인 평가가 초기화된다. 얻는 것은 대칭성뿐이라 수지가 안 맞는다.

### 쿠키·세션 전환은 쓰지 않는다

구현은 제일 쉽지만 **검색엔진이 번역 페이지의 존재 자체를 모른다.** 크롤러는 쿠키를 들고
오지 않으므로 URL 이 안 변하면 영어 페이지는 색인되지 않는다. 해외 유입이 목적인 작업에서
이 방식은 목적을 통째로 무효화한다.

언어 선택 UI 는 쿠키에 기록하되, **쿠키는 첫 진입 시 리다이렉트 힌트로만 쓰고 렌더링
언어는 항상 URL 이 결정한다.** 둘이 어긋나면 크롤러가 본 것과 사용자가 본 것이 달라진다
(cloaking 으로 오인될 수 있다).

## 5. 로케일 해석 파이프라인 — 이 설계의 핵심

### 문제

`SecurityConfig` 는 `anyRequest().authenticated()` 가 기본이고(`SecurityConfig:135`)
규칙이 전부 경로 리터럴이다(`/test/**`, `/balanceGame/**`, `/mypage/**` …).
`/en/test/abc` 가 생기는 순간 어떤 `permitAll()` 에도 안 걸려 **전 페이지가 로그인 화면으로
튄다.** 컨트롤러 `@RequestMapping` 도 마찬가지로 전부 못 찾는다.

### 해결 — 접두사를 벗겨서 체인에 흘린다

`LocalePrefixFilter` 를 **스프링 시큐리티 필터보다 앞에** 등록한다.

```java
// SecurityConfig 의 MultipartFilter 등록과 같은 방식.
// DEFAULT_FILTER_ORDER(-100) 보다 작을수록 먼저 실행된다.
// MultipartFilter 가 -101 이므로 로케일 필터는 -102.
registration.setOrder(SecurityProperties.DEFAULT_FILTER_ORDER - 2);
```

필터가 하는 일:

1. `/en/test/abc` 에서 접두사를 떼어 로케일 `en` 을 판정
2. 로케일을 request attribute 에 보관 (`LocaleContextHolder` 도 함께 설정)
3. `getRequestURI()` / `getServletPath()` / `getPathInfo()` 가 `/test/abc` 를 돌려주는
   `HttpServletRequestWrapper` 로 감싸 `chain.doFilter()` 로 넘긴다

**`RequestDispatcher.forward()` 를 쓰지 않는다.** forward 하면 현재 필터 체인이 중단되는데,
시큐리티 필터는 기본적으로 `DispatcherType.REQUEST` 에만 걸려 있어서 **인증·CSRF 검사가
통째�� 건너뛰어진다.** 래퍼 방식은 같은 요청·같은 체인을 유지하므로 이 구멍이 없다.

이 설계의 이득: **`SecurityConfig` 와 모든 컨트롤러 매핑을 한 줄도 고치지 않는다.**
체인 뒤쪽은 접두사의 존재 자체를 모른다.

> **구현 시 검증 필요** — Spring Boot 3.x MVC 는 기본적으로 `PathPatternParser` 를 쓰고
> `ServletRequestPathUtils` 에 파싱된 경로를 캐싱한다. 래퍼가 이 캐시보다 먼저 적용되는지
> 통합 테스트로 반드시 확인할 것. 어긋나면 매핑이 404 로 떨어진다.

### LocaleResolver

로케일은 URL 이 결정하므로, 필터가 넣어둔 attribute 를 읽기만 하는 구현을 둔다.
`setLocale()` 은 `UnsupportedOperationException` 을 던진다 — 요청 도중에 언어가 바뀌면
URL 과 렌더링 결과가 어긋나기 때문에, 조용히 통과시키는 것보다 즉시 실패하는 편이 낫다.

### 접두사 제외 경로

`/assets/**`, `/uploads/**`, `/profile/**`, `/favicon*`, `/manifest.json`,
`/robots.txt`, `/sitemap.xml`, `/.well-known/**` 는 로케일 접두사를 갖지 않는다.
필터와 링크 빌더(§7)가 **같은 목록**을 참조해야 한다. 한쪽만 고치면 정적 자원이 404 난다.

## 6. UI 문구 번들

### 배치

```
src/main/resources/messages.properties        ← 한국어 (기본 폴백)
src/main/resources/messages_en.properties
src/main/resources/messages_ja.properties
src/main/resources/messages_zh_TW.properties
```

한국어를 `messages_ko.properties` 가 아니라 **접미사 없는 `messages.properties`** 에 둔다.
어느 로케일에서든 키가 빠지면 한국어로 폴백되어, 최소한 화면은 깨지지 않는다.

### 설정

```properties
spring.messages.basename=messages
spring.messages.encoding=UTF-8
# 반드시 false. 기본값(true)이면 키가 빠졌을 때 "서버의" 시스템 로케일로 폴백한다.
# 운영 서버 로케일이 ko 라서, 영어 사용자에게 한국어가 튀어나오는데 로그에는 아무것도 안 남는다.
spring.messages.fallback-to-system-locale=false
```

### 키 네이밍

`화면.영역.용도` 3단 구성. 예: `test.result.share.button`, `common.confirm.delete`.
문장을 키로 쓰지 않는다(`"삭제하시겠습니까"` → 문구가 바뀌면 키도 바뀐다).

### 키 누락 검증 테스트

이 저장소 관례대로 "무엇을 보장하는가"를 한국어 `@DisplayName` 으로 적는다.

- `messages.properties` 의 모든 키가 en/ja/zh_TW 에도 존재하는가
- 반대로 번역 파일에만 있는 고아 키가 없는가
- `{0}` 같은 파라미터 자리표시자 개수가 로케일 간 일치하는가

**빌드에서 잡지 않으면 번역 누락은 배포 후 빈 화면으로 발견된다.** 파일 방식을 택한
가장 큰 이유가 이 검증이 가능하다는 점이므로 생략하지 말 것.

## 7. 링크 생성

템플릿의 `th:href="@{/test/abc}"` 가 로케일에 따라 `/en/test/abc` 를 뱉어야 한다.
템플릿 185곳을 일일이 고치는 대신 **Thymeleaf 링크 빌더를 교체한다.**

```java
templateEngine.setLinkBuilder(new LocaleAwareLinkBuilder());  // StandardLinkBuilder 확장
```

§5의 제외 경로 목록을 참조해 정적 자원에는 접두사를 붙이지 않는다.
**템플릿은 한 줄도 안 고친다.**

컨트롤러의 `redirect:` 문자열은 이 빌더를 타지 않는다. 리다이렉트 경로를 만들어 주는
헬퍼를 `common/` 에 하나 두고 그것만 쓰도록 한다 — `SecurityUtil` 을 한곳에 모은 것과
같은 이유다.

## 8. 캐시

`CacheConfig` 의 캐시 중 **로케일에 따라 내용이 달라지는 것**은 키에 로케일이 들어가야 한다.

| 캐시 | 로케일 의존 | 조치 |
|---|---|---|
| `CONTENT_LIST` | O | 키에 로케일 추가 |
| `ACTIVE_CATEGORIES` | O (`display_name` 이 사용자 노출 문구) | 키에 로케일 추가 |
| `PARTICIPANT_COUNT` | X | 그대로 |
| `EGEN_STATS` | X | 그대로 |

`MdTestUserService:202` 의 `@Cacheable(cacheNames = CONTENT_LIST)` 는 기본 키 생성기를
쓰므로 파라미터 조합이 곧 키다. **로케일을 안 넣으면 한국어 방문자가 채운 캐시를 영어
방문자가 그대로 받는다.** 예외가 나지 않고 그냥 틀린 언어가 나오는 종류라 발견이 늦다.

구현은 **메서드 파라미터로 로케일을 명시적으로 받는 쪽**을 택한다. 커스텀 `KeyGenerator`
로 숨기면 호출부에서 로케일 의존성이 안 보인다. `getAllContentList` 가 `includeSpicy` 에
기본값을 두지 않고 매번 명시하게 한 것과 같은 판단이다.

## 9. SEO

### hreflang

모든 색인 대상 페이지에 상호 참조를 넣는다.

```html
<link rel="alternate" hreflang="ko"        href="https://moondap.com/test/abc">
<link rel="alternate" hreflang="en"        href="https://moondap.com/en/test/abc">
<link rel="alternate" hreflang="ja"        href="https://moondap.com/ja/test/abc">
<link rel="alternate" hreflang="zh-Hant"   href="https://moondap.com/zh-TW/test/abc">
<link rel="alternate" hreflang="x-default" href="https://moondap.com/test/abc">
```

**상호 참조가 아니면 구글이 무시한다.** en 페이지가 ko 를 가리키면 ko 페이지도 en 을
가리켜야 한다. 자기 자신을 포함해 전부 나열한다.

### 1단계의 가장 큰 함정 — 번역 안 된 콘텐츠에 hreflang 을 달지 말 것

UI 만 번역한 상태에서 `/en/test/abc` 를 색인 대상으로 열면, 본문은 한국어 그대로인
페이지가 **4개 URL 로 중복 색인된다.** 사이트 전체가 "얇은 중복 콘텐츠"로 평가되어
지금까지 쌓은 것까지 깎인다. 애드센스가 붙어 있는 사이트에서 이건 실질적인 위험이다.

따라서 **1단계에서는 ko 이외 로케일 전체를 `noindex` 로 둔다.**
`SeoMetaInterceptor` 가 로케일이 ko 가 아니면 무조건 `noindex, follow` 를 넣게 한다.
hreflang 과 사이트맵 등록은 **콘텐츠 번역이 실제로 들어간 뒤에** 켠다.
이 한 줄이 1단계를 안전하게 만들어 준다.

### SeoMetaInterceptor 수정 항목

| 현재 | 변경 |
|---|---|
| `DEFAULT_TITLE` 한국어 상수 (46행) | `MessageSource` 조회 |
| `DEFAULT_DESCRIPTION` 한국어 상수 (47행) | `MessageSource` 조회 |
| `MAX_DESCRIPTION_LENGTH = 160` | 로케일별 상한. 구글은 픽셀 폭으로 자르는데 CJK 글자는 라틴보다 넓어서 ja/zh 는 **80자 안팎**이 실질 한계다 |
| `canonical` = baseUrl + requestURI | 래퍼가 접두사를 벗긴 뒤라 `/test/abc` 가 온다. **request attribute 에 보관해 둔 접두사를 다시 붙여야** 한다. 안 그러면 4개 로케일의 canonical 이 전부 한국어 URL 을 가리켜 번역 페이지가 통째로 색인에서 빠진다 |
| `NOINDEX_PATTERNS` | 접두사가 벗겨진 경로와 매칭되므로 **수정 불필요** |

### 사이트맵

`SitemapController` 는 1단계에서 **ko URL 만** 낸다. 2단계에서 로케일별 URL 과
`xhtml:link` 대체 링크를 추가한다. `MAX_CONTENT_URLS` 가 5,000 이므로 4개 로케일이면
20,000 — sitemap 단일 파일 상한(50,000)에는 여유가 있다.

## 10. 렌더링 — 한자 자형과 폰트

### `html lang` 이 하드코딩돼 있다

`layout/main_layout.html:4` 가 `<html lang="ko">` 로 고정이다. 로케일별로 바꿔야 한다.

이게 단순한 접근성 속성이 아닌 이유: **중국어와 일본어는 같은 유니코드 코드포인트를 다른
모양으로 그린다**(直, 骨, 今 …). 이른바 한중일 통합 한자(Han unification) 문제다.
브라우저는 `lang` 속성을 보고 어느 자형으로 그릴지 정하므로, `lang="ko"` 인 채로 일본어를
렌더링하면 **일본인 눈에 중국어 자형이 섞인 페이지**가 나온다. 기능은 멀쩡해 보이는데
현지 사용자에게는 바로 티가 난다.

zh-TW 는 `lang="zh-Hant-TW"` 로 둔다.

### 폰트

현재 로드하는 것은 Roboto / Poppins / Quicksand 셋뿐이고 **전부 CJK 글리프가 없다.**
한국어는 지금도 시스템 폰트 폴백으로 표시되고 있다.

**권장: 웹폰트를 추가하지 않고 `lang` 만 올바르게 준다.** `lang` 이 정확하면 브라우저가
OS 의 적절한 CJK 폰트를 고른다(macOS Hiragino/PingFang, Windows Yu Gothic/微軟正黑體).
Noto Sans JP/TC 를 서브셋 없이 얹으면 **수 MB** 라 모바일 로딩이 무너지는데, 디자인
일관성을 위해 치를 비용으로는 과하다. 서체 통일이 꼭 필요해지면 그때 서브셋 파이프라인을
만든다(현재 저장소에 빌드 파이프라인이 없다는 점도 고려 — `package.json` 없음).

## 11. 콘텐츠 번역 스키마 (2단계)

### 별도 번역 테이블을 쓴다

```sql
-- 언어 중립 데이터만 남긴다
-- md_test (id, test_key, thumbnail_image, category, test_type, status, play_count, ...)

CREATE TABLE md_tests_i18n (
    test_id     BIGINT       NOT NULL,
    locale      VARCHAR(10)  NOT NULL,   -- 'ko','en','ja','zh-TW'
    title       VARCHAR(255) NOT NULL,
    description TEXT,
    PRIMARY KEY (test_id, locale)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE md_test_questions_i18n (
    question_id   BIGINT      NOT NULL,
    locale        VARCHAR(10) NOT NULL,
    question_text TEXT        NOT NULL,
    PRIMARY KEY (question_id, locale)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE md_test_results_i18n (
    result_id      BIGINT       NOT NULL,
    locale         VARCHAR(10)  NOT NULL,
    result_title   VARCHAR(255) NOT NULL,
    result_content TEXT,
    PRIMARY KEY (result_id, locale)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- md_content_category.display_name, md_balance_game 도 같은 형태로.
```

**콜레이션을 `utf8mb4_unicode_ci` 로 맞춘다.** 서버 기본값(`utf8mb4_0900_ai_ci`)으로
만들면 기존 테이블과 JOIN 할 때 `Illegal mix of collations` 로 조회가 실패한다
(`local_dev_schema.sql` 머리말에 같은 함정이 기록돼 있다).

### `title_en`, `title_ja` 컬럼 추가 방식을 쓰지 않는 이유

언어를 하나 추가할 때마다 DDL + 모든 쿼리 수정이 된다. 번역 테이블이면 언어 추가가
`INSERT` 다. 지금은 4개지만 늘어날 여지가 있다.

### 번역 누락 폴백

```sql
SELECT COALESCE(i.title, k.title) AS title   -- 번역이 없으면 한국어 원문
  FROM md_test t
  LEFT JOIN md_tests_i18n i ON i.test_id = t.id AND i.locale = #{locale}
  LEFT JOIN md_tests_i18n k ON k.test_id = t.id AND k.locale = 'ko'
```

`getAllContentList` 의 UNION 쿼리는 지금도 인덱스를 못 타는데 JOIN 이 더 붙는다.
캐시가 전제라는 사실이 더 강해질 뿐 구조가 바뀌지는 않는다.

### 파급 범위

- 매퍼 XML 1,007줄 대부분
- 어드민 등록·수정 폼 6~7개(`insertTestView`, `updateTestForm`, `insertBalanceGame`,
  `insertTestMobileView` …)를 로케일별 입력으로 개편
- 콘텐츠 변경 시 `@CacheEvict(CONTENT_LIST, allEntries = true)` 는 그대로 유효

## 12. 로케일에 묶인 기존 로직

| 대상 | 문제 | 조치 |
|---|---|---|
| `ProfanityUtil` | 한국어 전용. 자모(`ㅅㅂ`)·로마자 변형(`tlqkf`)까지 다룬다. en/ja/zh 댓글에는 무용지물 | 로케일별 단어 목록 분리. 광고 게재 페이지에 혐오·성적 표현이 노출되면 애드센스 정책 위반이므로 1단계에서도 **번역 페이지에 댓글을 여는 순간** 필요해진다 |
| 에겐테토 | 한국 인터넷 밈. 24문항·결과 유형이 DB 가 아니라 `egenTeto/questions.html`(98줄) / `result.html`(134줄) 에 하드코딩 | **i18n 대상에서 제외.** 번역해도 현지에서 의미가 통하지 않는다 |
| 날짜·숫자 포맷 | 감사 필요 | 템플릿·서비스의 포맷 코드를 훑어 로케일 인지 포맷으로 교체 |
| 이미지 내 텍스트 | 썸네일·결과 이미지에 한글이 박혀 있으면 번역 불가 | 감사 필요 |

## 13. 실행 순서

### 1단계 — 골격 (약 3~4일, DB 무수정)

1. `LocalePrefixFilter` + `LocaleResolver` + 필터 순서 (§5)
2. 로케일 인지 링크 빌더 (§7)
3. `messages*.properties` 신설, 템플릿 `#{...}` 치환 (§6)
4. `html lang` 로케일별 출력 (§10)
5. **ko 이외 전부 `noindex`** (§9) ← 이게 1단계를 안전하게 만든다
6. 키 누락 검증 테스트

되돌리기 쉽고 DB 를 건드리지 않는다. 골격이 맞는지 여기서 검증한다.

### 2단계 — 콘텐츠 (3주+)

7. 번역 테이블 신설 + 기존 데이터 `locale='ko'` 로 이관 (§11)
8. 매퍼 XML 개편, 캐시 키에 로케일 추가 (§8)
9. 어드민 폼 로케일별 입력 개편
10. 번역 본문 확보 ← **일정의 실질적 병목**
11. 번역이 들어간 로케일만 `noindex` 해제, hreflang·사이트맵 켜기 (§9)

### 3단계 — 운영

12. `ProfanityUtil` 로케일별 분리 (§12)
13. 서치 콘솔에 로케일별 색인 추적

## 15. 열린 질문 — 착수 전 결정 필요

1. **번역 조달** — 기계번역 그대로 올린 본문은 애드센스가 "저품질 자동생성 콘텐츠"로
   본다. UI 문구는 기계번역으로 충분하지만, 결과 본문(유형당 약 1,000자)은 판단이 필요하다.
   × 3개 언어이므로 물량이 작지 않다.
2. **1단계만 하고 멈출 것인가** — 멈춘다면 ko 이외는 계속 `noindex` 다. 즉 **해외 검색
   유입은 0** 이고, 얻는 것은 "링크로 직접 들어온 외국인이 UI 를 읽을 수 있다"뿐이다.
   수익이 목적이라면 2단계까지 가야 의미가 생긴다.
3. **기존 콘텐츠 번역 vs 현지 신규 제작** — 한국 정서에 기댄 테스트는 번역해도 현지에서
   잘 안 통한다. 2단계 비용을 쓰기 전에, 영어권용 콘텐츠를 새로 만드는 쪽이 나은지
   비교해 볼 가치가 있다.
